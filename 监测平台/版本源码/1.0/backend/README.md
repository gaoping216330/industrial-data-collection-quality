# OA、kepserver数据监测平台



局域网页面：<http://192.0.2.10:8789/>，本机也可用 <http://127.0.0.1:8789/>。Windows 防火墙仅允许 `192.0.2.10/16` 访问 TCP 8789；其他网段要按实际路由再配置。接收服务仍在 8788。启动 `start-background.ps1` 会分别启动基础判定、模型判定和页面，三个进程独立于采集服务。登录后任务 `DataQualityMonitor-StartAtLogon` 延后 2 分钟启动它们。



数据范围按 `autosensor.tag=0`：Kepserver 为 `channel='kepserver'`，OA 为 `channeloa='oa'`。同一 EID 同时属于两者时由 Kepserver 持有。点位目录来自 MySQL，实际收到时间来自 Redis 的 `dq:cache:receipt`，数值来自 `dq:cache:latest:<eid>`。发送时间与实际收到时间分开；Kepserver 整包 `timestamp` 为发送时间、单点 `t` 为上次变化时间。历史保留 60 分钟。



基础判断每轮约 10 秒：从未收到、停止发送（网络收到后超过 10 秒）、发送时间超前/滞后（以网络收到时间为参照，绝对误差超过 10 秒）、Kepserver 质量位 BAD，以及 5 分钟恒值。Kepserver 本机缓冲排队超过 10 秒时，尚未解析出的点位显示“本机积压待判定”，不会误判为现场停止发送。设备全部参与判定的数值点位持续恒值为设备恒值异常；部分恒值且有其他同设备点位变化为恒值传感器异常。BOOL 与未标注数值类型不参加恒值。OA 恒值默认关闭，可在页面开启。接收链路有缺口、连续接收时间不足或缺少上次变化时间时显示无法判断。



结果只写新表 `dq_point_quality_current`、`dq_device_quality_current`、`dq_quality_event`、`dq_quality_rule`，不修改 `autosensor`。当前点位状态按最新数据更新；发送时间异常事件需要持续 30 秒才打开或关闭，避免临界波动重复生成事件。其他异常出现时开事件、恢复时关闭。本机 Windows 授时源已核对为 192.0.2.10（2026-10-23）。



模型进程使用项目 D 盘中的 `.python312` 运行环境和原模型依赖，已实际加载 390 个 ready 模型、11 个模型组，输入为 Redis 中按整包发送时间记录的最近 45 分钟 Kepserver 数据；它不再单独订阅 MQTT。首次运行或采集发生缺口后须先积累连续 35 分钟历史，期间页面显示“历史窗口预热”，不会提供推理结果。真实推理每 5 分钟执行一次，结果写 `dq_model_quality_current`，不修改 `autosensor`。



网页目前没有登录校验；在放行的内网地址范围内，访问者也可以修改判定配置。若后续需要不同人员只读或管理权限，应加用户登录和权限控制。



页面当前可见的数据列表和弹窗每 10 秒自动刷新，保留筛选条件与分页；后台标签页暂停轮询，避免堆积请求。总览中的“从未接收”“停止发送”“异常点位”可点击，先按采集设备及四级业务归属列出设备、总点位与受影响点位数，再展开 EID 明细、负责人、最后接收时间及无数据开始时间。停止发送的无数据开始时间按最后接收加 10 秒计算；从未收到只展示首次记录时间，不能代表监测前已离线多久。



总览“最近未恢复设备事件”位于点位事件上方，按未关闭事件汇总设备和四级业务归属，异常点位按 EID 去重，列出负责人、来源、原因、当前最早未恢复开始时间。结束时间为空时显示“未恢复”。点击设备或异常点位数可展开该设备各点位的负责人、原因、开始/结束时间；“查看全部设备”支持分页。下方“最近未恢复事件”增加 department、process、equipment、group、point 和负责人。设备汇总仅聚合点位事件，并非额外认定整台 PLC 离线。



所有设备列表和设备点位弹窗固定标题、摘要与表头，仅数据行区域滚动；表格使用 15px 字体、加粗浅蓝表头、清晰行线和隔行底色。10 秒自动刷新保留同一筛选与分页下的滚动位置。样式位于 static/dialogs.css。



Kepserver 与 OA 的业务展示统一使用 department、process、equipment、group。MySQL 展示视图为 `dq_point_quality_display`、`dq_device_quality_display`、`dq_quality_event_display`，页面使用这些视图。Kepserver 采集设备判定仍按 device_name，多个业务归属在设备页面分别展示。按用户确认，负责人使用 autosensor.createdBy；字母代码通过 dq_person_directory 转为中文姓名。当前在用的 7 个代码已按截图录入。同设备多个负责人去重列出，未登记代码原样显示。初始映射见 personnel.json。





### 2026-10-27 异常确认与设备恒值规则（替代前述即时报警和30秒时间异常防抖）



后台目标每10秒观察一次，对每个EID、每个原因独立计时；新增原因须连续观察满300秒，期间恢复或观察间隔超过40秒则候选计时重置。正式点位状态、设备汇总、异常事件及摘要每300秒发布一次；网页仍每10秒刷新，显示最近一次正式判定时间。未满足确认时长显示“异常待确认（连续5分钟）”及“待判定”，不计入异常数。已有未关闭事件在其原因仍然存在时继续保留；恢复在下一次正式发布时写入恢复时间。确认后的事件开始时间回记首次观察到该原因的时间，确认后在发布前恢复的事件也保留起止时间。观察进程重启后未确认候选重新计时，既有事件不删除。



恒值来源默认阈值为600秒，保留设备/点位单独覆盖及OA默认关闭设置。恒值仅对同一采集设备全部参与的非BOOL数值点均为flat时产生“设备恒值异常”；部分点位flat、其他点位moving时不再产生“恒值传感器异常”。单传感器异常由模型判定。600秒是基础恒值窗口，达到后仍遵循新增异常300秒确认和下一次正式发布，故页面出现恒值异常可能晚于10分钟。当前/历史数值仍照常实时更新和5秒采样，不受正式发布周期影响。模型自身运行周期与输出规则未修改。



验证：15项异常确认、事件缓冲、设备恒值、既有质量规则和网页响应回归测试通过；JS语法检查通过。
