# 独立 OA / MQTT 实时缓存服务

该服务独立于网页和模型程序运行，数据库仅用于读取点位目录。实际值写入本机 Redis，不写 MySQL。

## 接收地址

`POST http://192.0.2.10:8788/api/ingest/winccoa`

发送端 IP：`192.0.2.10`。Windows 防火墙及应用均限制此来源；本机也可用于诊断。

请求头：`Content-Type: application/json`。按用户要求不校验 `X-API-Key`，发送端无需添加此请求头，来源限制由 IP 白名单执行。

请求体支持直接 JSON 数组，也兼容 `{"values": [...]}`：

```json
[
  {"0":"15c62eac","1":1792652231045,"50":0,"99":1764040121617},
  {"0":"ee18151b","1":1792652231045,"50":6300,"99":1769629196913}
]
```

- `0`：EID。
- `1`：发送时间，毫秒 Unix 时间戳。
- `50`：当前值，数值或布尔值；0 是有效值。
- `99`：最后一次值改变时间，毫秒 Unix 时间戳，不作为发送时间或掉线时间。
- 兼容旧字段 `eid/id`、`v/value`、`t/timestamp`、可选 `q`。
- 每批最多 2000 条，请求体最多 4MB。

## 目录筛选及来源优先级

目录只读查询数据库 `192.0.2.10:3306/gpwinccoa.autosensor`，账户由配置读取，目前使用用户提供的 `root1`。

- Kepserver：`tag=0 AND channel='kepserver'`。
- OA：`tag=0 AND channeloa='oa'`，其中 Kepserver 点位不允许 OA 写入，即使 Kepserver 暂时没发值，也不自动用 OA 替代。
- 目录每 60 秒刷新；成功目录最多沿用 5 分钟。首次读取失败或目录超时，停止接收写入并明确返回 503，避免绕过筛选。
- 2026-10-22 核对：Kepserver 30643 个，OA 6896 个，交集 454 个，OA 去重后 6442 个。
- MQTT 从既有模型服务配置读取 broker 和 topics，独立订阅。报文按 EID 目录校验，与来自哪个 topic 无关。
- MQTT Client ID 固定为 `readMqt_redis`。修改 Client ID 不会自动启用采集。启用后可在 RabbitMQ Queues 中查找 `mqtt-subscription-readMqt_redisqos0`（QoS 0）。
- 2026-10-23 优化后已恢复订阅，实际开关以 `cache_config.json` 中的 `mqtt_enabled` 为准。

## HTTP 返回

- 200：`received` 为输入条数；`cached` 为真实写入数；`ignored` 为目录/来源不允许；`invalid` 为格式错误；`stale` 为旧时间报文；`duplicate` 为相同报文。
- 403：发送 IP 不允许。
- 400 / 413：格式错误 / 批次或报文过大。
- 503：目录不可用或 Redis 写入失败。发送方应重试，不应当作已缓存。
- `GET /health` 可检查接收器和 Redis/目录是否可用；不返回密钥或点位数据。
- `GET /api/cache/status` 受同样的 IP 白名单限制，用于查询累计接收统计。

## Redis 数据

数据库 0，前缀 `dq:cache:`。

- `catalog`：Hash，EID -> `kepserver` / `oa`。
- `latest:<eid>`：JSON，含 `eid/value/quality/source/source_time/last_change_time/received_time`。保留最后一条，需根据接收时间自行判断是否新鲜。
- Kepserver 时间含义已由用户确认：`source_time` 取整包外层 `timestamp`（发送时间），`last_change_time` 取点位内 `t`（最后变化时间），`received_time` 为本机接收时间。新 Kepserver 记录带 `time_schema=2`，即使值和变化时间不变，新发送时间也应形成新样本。
- 对应历史 Stream 中 `t` 为整包发送时间、`c` 为最后变化时间，并带 `schema=2`。改造前已有历史不重写：无 schema 或 schema=1 的旧 Kepserver 历史中 t 曾表示变化时间，不能当作发送时间使用；旧记录随 60 分钟保留期自然清理。
- Kepserver 整包缺少 `timestamp` 时记录报文错误和历史缺口，不使用点位变化时间冒充发送时间。OA 仍按 1=发送时间、99=最后变化时间映射。
- `history:<eid>`：Stream，字段 `t/v/q/c/s`。ID 为 Redis 接收时间，`t` 为源时间。滚动保留最近 60 分钟接收记录，并每 60 秒清理一次；停止更新的历史自动过期。消费方查询时应以所需时间窗口再次过滤，维护调度可能有少量延迟。
- `stats:oa` / `stats:kepserver`：累计条数、最后批次接收时间及结果。
- 原始值、质量码与发送时间不等于模型检测结果，本服务未执行模型推理。

相同来源的旧时间记录不会覆盖新值；相同时间、值、质量、最后改变时间的重复记录不会再次写历史。Kepserver 优先由共享目录和 Redis 原子脚本共同执行。

## MQTT 并发及积压保护（2026-10-23）

- 网络回调只入缓冲，不执行 JSON 解析、SQL 或 Redis 操作。
- 当前四个解析/写入线程，`mqtt_intake.writer_threads` 可配置 1～4。按 Topic 固定分配，保持同一 Topic 内顺序。Redis 仍校验时间及来源，避免并发旧值覆盖新值。
- 使用 orjson 快速处理合法 JSON，兼容旧网关包含未转义控制字符的字符串。
- 目录预先加载到本机，过滤不属于对应来源的点位；已提交的重复 MQTT 记录可在本机跳过。
- Redis 每批最多 500 个点位使用一次 Lua 调用，保留原有 latest/history 结构。
- 本地缓冲最多 10000 包、200MiB。正常情况下不丢已收到的延迟报文，`discard_expired_packets=false`；硬上限被突破时仍会丢弃最旧包并记录缺口，不能承诺无限缓冲或绝对零丢失。
- 正在处理的包耗时超过 20 秒，每 10 秒检查一次，连续 3 次超限触发保护性断开。本地排队等待时间仍统计，但不再单独触发此规则。
- 只读检查 RabbitMQ 管理接口中的本程序队列：每 60 秒一次，Ready >10000 包或 Ready 消息体 >200MiB，连续两次超限时断开；冷却 30 秒后重连。管理接口无权限或不可用时明确报告未知，不当作零积压；此时仍有本机缓冲保护。
- 断开期间，已在本机缓冲的包继续处理，不因冷却主动清空。
- MQTT 3.1.1，QoS 0，Clean Session=true。断开后不保留本订阅的离线积压；断开期间的消息无法保证补回。
- `history_gaps:kepserver` Stream 记录启动、断线、过载、缓冲丢弃、写入失败等缺口。`mqtt_runtime` Hash 每约 10 秒更新状态、缓冲、处理耗时、丢弃和保护次数。状态接口也返回这些字段。发生缺口后 `history_complete=false` 至少维持一个 60 分钟窗口；新模型消费程序应检查此标记，不能默认为历史完整。
- `received_time` 为网络回调实际收到报文的时间，不是后台写入完成时间。

运行 `D:\python313\python.exe monitor_mqtt.py --samples 7 --interval 10` 可只读采样本机和服务端队列。监测程序不建立额外 MQTT 订阅。

服务端队列限额尚未修改。若后续要配置 RabbitMQ Policy，范围应精确限制为 `^mqtt-subscription-readMqt_redisqos0$`，不能对所有业务队列设置统一限额；长度上限和 `drop-head` 会主动丢弃旧消息，需要接受其历史缺口。当前保护由本机监测和主动断开实现。

## 运行与排查

- `start-background.ps1`：启动 Redis 后在后台启动接收器，已运行时不重复启动。
- `start-receiver.cmd`：前台运行，适合手动排查；后台接收器运行时不要重复执行，以免占用同一端口。
- 运行 PID 记录在 `receiver.pid`；停止前应核实对应进程确为本服务，Redis 不随接收器停止。
- 日志：`logs/receiver.log`，按大小轮转。可按 `remote=192.0.2.10` 查找真正来自 OA 的请求，不能把本机测试当作实际到达。
- 六项自动测试在唯一临时 Redis 命名空间中验证字段映射、来源优先、乱序/重复保护、鉴权、数据库不可用和历史清理，结束后清理测试键。
- Windows 当前用户登录后任务 `DataQualityCacheReceiver-StartAtLogon` 启动接收器。首次任务配置完成后仍须核对任务执行结果。

配置包含数据库凭据和接口密钥，已在本目录 `.gitignore` 排除，不要提交或外发。

## 当前边界

本服务占用 8788 端口，旧 `local_platform/app.py` 也配置了 8788。两者不能同时绑定同一端口，网页后续应调整端口或统一入口。

旧平台页面、旧模型推理服务尚未改为读取此 Redis 缓存。本服务只负责独立采集、筛选、缓存。

Redis 最大数据内存 4GB；到达上限会拒绝写入，应用返回/记录失败，不能保证当前容量足够全厂所有点位连续一小时。实际容量需在运行中测量，必要时调整内存或历史范围。


### OA 接口返回状态

POST `/api/ingest/winccoa` 返回增加 `success`（布尔值）和 `status`（`success` 或 `error`）。HTTP 200 且 `success: true` 表示本批请求已处理；并不表示全部点位均写入，具体查看原有 `cached`、`ignored`、`invalid`、`stale`、`duplicate` 计数。非 2xx 返回 `success: false`、`status: "error"`，保留错误及可重试信息。


### 2026-10-27 采集性能调整

4 个 MQTT 工作线程动态领取空闲 Topic，同一 Topic 串行处理。OA 与 Kepserver 共用本机接收时间的 5 秒采样窗口，每点每窗口至多新增一条历史，仅保存发送时间 `t` 和实际值 `v`；窗口对齐不意味着两路数据发送时间完全相同。最新值、接收时间和当前质量仍逐包更新。历史保留 60 分钟，旧格式随正常清理逐步退出，不批量删除。Kepserver BAD 或未知质量值保留在最新状态中，但不进入供模型使用的精简历史；模型兼容旧 schema 2 和新 t/v 历史。历史清理批次间增加短暂让步，减轻实时写入压力。原有 200 MB 队列和熔断阈值不变。

验证：19 项采集回归测试在独立 6389 Redis 实例全部通过，模型新旧历史兼容检查通过。生产实例已抽查 OA 与 Kepserver 均写出仅 t/v 的历史记录。上线时 Redis 仍有后台快照及磁盘页等待，本机积压未消除，不能将上线等同于吞吐恢复。


### 2026-10-27 整五秒时间对齐（替代前述按本机接收窗口采样）

OA 使用字段 1，Kepserver 使用整包 timestamp。仅采样发送时间秒数为 00、05、10…55 的数据，该秒内取首条，历史 t 去掉毫秒并记为整五秒毫秒时间戳；同 EID 同目标秒最多一条。延迟接收不改变采样所属秒；不以其他秒补齐缺失目标秒。最新值保留原始毫秒发送时间并逐包更新。历史旧记录不改写，随 60 分钟保留期自然退出。21 项回归测试已在独立 Redis 实例通过，包括两路接收延迟不同仍对齐、缺失目标秒不补值。


### 2026-10-27 动态来源

目录常规刷新600秒；每5秒检查版本通知，收到同步程序新版本后提前刷新。目录就绪有效期1260秒，避免正常10分钟刷新间隔导致中间5分钟拒绝接收。历史清理仍每60秒执行。来源切换或退出目录会原子清除旧最新值和接收记录，将旧来源历史改名为 history_archive 并保留TTL，新的当前历史重新建立整五秒采样；不把OA精简历史当成Kepserver模型输入。Kepserver快速写入脚本再次核对Redis目录，防止已在处理的旧任务绕过新归属。OA与Kepserver重复仍以Kepserver为主。


2026-10-27：历史保留期调整为180分钟（3小时），保持整五秒采样和逐包更新最新状态。总览显示所有适用的正式异常原因，包括零值，整行可点击进入设备及点位明细；设备监测改为部门、工序、设备、组、来源、归属人员联动下拉筛选。页面仍随正式判定及目录变更更新。
