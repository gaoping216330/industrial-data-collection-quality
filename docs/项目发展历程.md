# 项目发展历程

本项目来自长流程钢铁厂的数据采集与运维实践。时间、规模和问题均为项目经验描述，不代表所有同类产品的表现。厂区名称在本版中省略，

## 四代总览

|阶段|时间|采集与存储链路|主要变化|
|---|---|---|---|
|第一代：Java直采|2019年以前|PLC → Java → 本地MySQL → 同步程序 → 中心MySQL|定制采集、本地缓存、集中同步|
|第二代：KEPServer|2020年|PLC → KEPServer / OPC Server → ODBC → MySQL|从写代码转向配置点位|
|第三代：WinCC OA与数据中台|2022年|WinCC OA → HTTP POST → Kafka → ClickHouse；Redis提供实时缓存|统一数据池、EID目录和时间口径|
|第四代：工业物联网|2024年|分厂PLC网络 → 工业NAT → KEPServer集群 → MQTT → 数据中台|集中采集、消息解耦、以数据流作为监测入口|

四代描述采集体系演变，与本仓库网页1.0、1.1的版本编号不同。

## 第一代：Java直采时代

### 架构与做法

Java程序读取PLC数据块，先写入现场MySQL，再通过生产网同步至中心数据库。现场采集机使用双网卡分别连接PLC网与生产网。新增点位通常需要调整PLC数据块和Java程序。

~~~mermaid
flowchart LR
    PLC[PLC数据块] --> Java[Java采集程序]
    Java --> Local[现场MySQL]
    Local --> Sync[生产网同步程序]
    Sync --> Center[中心MySQL]
~~~

### 收获与问题

架构简单，本地存储能够缓冲断网期间的数据，支持少量写入操作。但采集机数量多、维护量大，数据分散在各表，统一查询困难。没有完善的断线监控，常由用户反馈后才发现故障。点位变更涉及采集程序和PLC，维护成本较高。

双网卡本身不等于物理隔离，实际安全性取决于网络边界、路由转发与访问控制。

## 第二代：KEPServer配置化采集

KEPServer作为OPC Server读取多个PLC，通过ODBC写入数据库。按当时的实施方案，每个PLC对应独立数据表，支持自动建表和点位导入导出。

~~~mermaid
flowchart LR
    PLC[多台PLC] --> KEP[KEPServer / OPC Server]
    KEP --> ODBC[ODBC写入]
    ODBC --> DB[按PLC组织的MySQL数据表]
~~~

采集由Java开发转向点位配置，不再要求PLC侧专门整理采集数据块。按当时项目经验，稳定性和容错能力提高，单连接对部分老旧PLC较友好。

不足是数据仍分散在多张表，缺少统一数据字典；写入功能需要另外开发Python程序，项目中曾遇到长时间运行后的内存问题。现场采集机的维护负担仍然存在,现场采集机建议用工控机。

## 第三代：WinCC OA与数据中台

2022年阶段以82台采集机和3万以上点位为项目规模背景。前置机由驱动读取现场数据，按每包约1000个点位通过HTTP POST发送至数据中台。

~~~mermaid
flowchart LR
    OA[WinCC OA前置机] --> HTTP[HTTP POST / 每包约1000点]
    HTTP --> Kafka[Kafka消息队列]
    Kafka --> CH[ClickHouse历史存储]
    CH --> Redis[Redis实时缓存]
    Redis --> Apps[查询与实时展示]
~~~

统一数据池、Sensor / EID点位目录和时间口径，使集中管理、跨设备查询、数据对齐及实时展示更加方便。

项目中的主要问题包括点位配置需要修改4—5处、采集效率未达预期、接口异常后的内存崩溃、驱动或软件缺陷，以及大量现场采集机的维护。

PPT将该现场的WinCC OA采集效率描述为KEPServer的约五分之一。由于没有同协议、同硬件、同负载的测试记录，该数字仅作为项目经验，不作为通用产品性能基准。

## 第四代：工业控制网与MQTT

2024年阶段通过工业控制网和MOXA工业NAT接入分厂网络，以集中KEPServer集群采集，并经MQTT消息服务送入数据中台。

~~~mermaid
flowchart LR
    Plants[各分厂PLC网络] --> NAT[工业NAT / MOXA地址映射]
    NAT --> KEP[集中KEPServer集群]
    KEP --> MQTT[MQTT消息服务]
    MQTT --> Platform[数据中台 / Redis / Kafka / ClickHouse]
    MQTT --> Quality[采集与质量监测]
    DCS[部分DCS数据] --> OA[保留WinCC OA接入]
    OA --> Platform
~~~

PPT记录约3万点位迁移到KEPServer，约6000点位继续由WinCC OA接入。后者是在当时驱动、授权和协议条件下，部分DCS未能接入KEPServer，不代表相关厂商所有设备普遍不兼容。

主要收益是采集从分散走向集中：PPT记载由82台采集机转向5台集中服务器；MQTT将采集与消费解耦，也成为数据质量监测的入口。点位配置和消息订阅能够与后续业务相对分开维护。

主要挑战是工业网络建设投入、NAT映射管理、协议兼容和长链路排障。网络分区与NAT需要配合实际访问控制，不能单凭这些组件就认定安全隔离已经完成。

## 历史经验与本仓库的关系

历史图示描述整个工厂的数据平台，不表示本仓库已实现全部Kafka、ClickHouse或PLC驱动功能。当前仓库围绕OA和Kepserver MQTT的数据接收、实时缓存、趋势展示、点位与设备异常、模型结果、人工原因、目录同步和运行诊断展开。

历史经验形成了以下需求：

1. 区分现场设备断线、采集链路异常和平台自身故障。
2. 对恒值、质量BAD、重复发送提供可解释的检查，并降低无效报警。
3. 统一点位字典、设备归属及负责人关联，减少多处维护。
4. 将模型结果与本点、关联点趋势结合，支持人工复核。
5. 为长时间运行、超时重连和故障恢复保留可追溯记录。

以上是需求和代码范围说明，不构成生产稳定性保证。仓库仅含脱敏源码和示例配置，不含生产凭据、现场数据库和模型训练产物。
