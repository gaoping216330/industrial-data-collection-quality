# 工业数据采集与质量监测平台

Industrial Data Collection & Quality Monitoring

面向钢铁生产现场的传感器数据接入、采集状态监测、数据质量判定和模型辅助分析平台。系统对接 WinCC OA 与 Kepserver MQTT，将现场数据、点位目录、设备归属和人员信息关联起来，在同一网页中查看实时数值、趋势、异常及处理原因。

**项目最初使用轧钢数据开展试点；当前运行版本已将全厂传感器数据纳入系统，不再局限于轧钢、单一产线或某几个测点。用于模型检测的目标点位，则经过人工筛选，选择能够作为现场检测点的数据，再结合模型验证状态投入检测。**

“全量接入”不等于“每个点位都使用模型”，也不等于“每个点位始终启用全部报警规则”。

## 1. 项目背景与当前范围

项目从轧钢现场数据出发，先验证如何利用生产工况和同设备相关信号判断传感器数据是否合理，随后扩展至全厂数据接入、设备监测和质量管理。

当前运行范围由生产点位目录维护，覆盖已纳入系统的全厂传感器数据。部门、工序、设备、组、EID、点位名称、来源和负责人用于检索、分组和异常追踪。具体数量随目录同步和现场调整变化，本README不把某次运行时的点位数量写成固定规模承诺。

|范围|含义|
|---|---|
|数据接入范围|当前运行系统已纳入全厂传感器数据，统一接收和展示|
|规则检测范围|结合点位配置、数据状态与各类规则判断，不要求每个点位启用所有规则|
|模型检测目标|经过人工筛选、可用于现场检测的目标点位；并按模型验证资格决定是否参与正式推理|
|关联点与状态量|为工况识别和目标分析提供上下文，不自动成为模型检测目标|
|停用检测的点位|仍可保留采集、当前值和趋势，停用检测不等于删除数据|

早期文档中的特定轧机、目标EID、历史文件和训练参数属于试点资料，不能据此理解当前系统的覆盖范围。

## 2. 系统要解决的问题

- 数据有没有持续到达，异常发生在现场点位还是采集与监测平台本身？
- 当前值是否可信，是否存在质量BAD、停止发送、恒值或重复发送？
- 哪个部门、设备、点位受到影响，应该由谁排查？
- 异常从何时开始、持续多久、是否恢复，人工排查原因是什么？
- 模型判断异常时，本点和关联点的趋势是否支持这一结论？

系统提供监测和辅助分析，不把模型异常直接等同于仪表物理损坏，也不替代现场联锁或安全控制系统。

## 3. 数据流与系统边界

~~~mermaid
flowchart LR
    OA[WinCC OA数据] --> HTTP[HTTP接收]
    KEP[Kepserver数据] --> MQTT[MQTT订阅]
    HTTP --> Cache[Redis最新状态与趋势]
    MQTT --> Cache
    Directory[点位目录] --> Monitor[规则与设备判定]
    Cache --> Monitor
    Cache --> Models[人工筛选目标的模型推理]
    Monitor --> DB[MySQL结果与事件]
    Models --> DB
    Cache --> Web[监测网页]
    DB --> Web
    History[历史数据接口] --> Web
~~~

当前代码侧重接收已有OA与MQTT数据并进行质量监测；全厂历史平台中的PLC驱动、工业NAT、Kafka和ClickHouse，不应仅因出现在历史架构文档中就被视为本仓库全部实现的组件。自研统一采集配置与协议接入属于后续规划方向。

## 4. 主要功能

### 采集状态与总览

统一查看OA、MQTT、Redis、数据库与判定服务的状态，汇总点位和异常分布，并按部门、工序及人员查看统计。区分“设备数据异常”与“平台不可用、现场状态未知”，避免将基础设施故障直接当成所有设备离线。

### 设备与点位监测

按部门、工序、设备、组、EID、名称、来源、负责人及状态筛选；支持多个EID查询。业务设备按部门、工序、设备和组的归属关系组织，不把每个采集标识都视作独立设备。

点位页面提供当前值、最近收到时间、判定原因和检测开关；当前页实时数据按约5秒刷新。正式判定采用独立发布节奏，实时值刷新不代表异常状态每5秒重新确认。

### 数据质量规则

|检查方向|说明|
|收包与断线|观察从未收到、停止发送及数据时效，并对持续异常确认|
|质量位|结合接收数据的质量字段判断；不同来源按对应协议语义处理|
|恒值|结合配置时间窗口和设备内参与点位共同状态判断，避免随意将单点稳定值判为设备故障|
|重复发送|检查MQTT重复或冲突发送，提供EID、地址及历史跟踪信息|
|平台健康|检查接收、缓存与判定链路，故障期间避免生成不可靠的现场结论|

默认运行策略为约10秒观察、持续5分钟确认异常、约5分钟发布正式结果。恒值窗口及部分规则可按来源、设备或点位配置；具体以部署版本和本地配置为准。

### 模型辅助检测

模型目标点位由人工筛选。人工筛选决定哪些数据适合承担现场检测任务，不代表每条历史样本已经人工标注，也不代表模型已经通过性能验证。

模型部署还需要独立验证资格。当前策略仅将通过验证、符合启用条件的模型用于正式检测；训练完成、已生成模型、通过验证和当前判断正常，是不同概念。

模型结合历史工况、目标点位及相关信号给出判断、健康度和解释。用户可以查看关联点及趋势进行人工复核。关联点按需选中加载，避免打开点位详情时同时加载全部曲线。

历史窗口不足、数据中断或关联信号不足时，应显示无法判断或相应说明，不能强行输出正常。不同类型模型的训练和验证方法可能不同，不能把早期试点参数当作全厂统一算法。

### 趋势与导出

每个点位提供最近约180分钟的实时趋势；历史查询支持秒级原始、分钟平均、小时平均和天平均，并选择开始与结束时间。曲线支持游标、时间数值查看、移动、缩放和导出；历史接口按单次最多3600条的约束组织查询。

Redis趋势按约5秒保存样本。缓存保留3小时不代表其中必然没有断点；页面显示两位小数，缓存可保留原始数值精度供分析。

### 人工处理与权限审计

管理员可以操作点位报警和恒值检测开关，并记录相关修改。设备人工填写的异常原因可关联显示到点位和事件，支持追踪恢复时间和持续时长。普通管理员与超级管理员的人员管理权限分开，具体以部署版本为准。

关闭报警不代表停止接收。采集、趋势和检测启用状态应分别理解。

## 5. 存储与运行方式

|组件|用途|
|---|---|
|Redis|最新点位值、收包状态、短期趋势和运行状态|
|MySQL|点位目录副本、判定结果、异常事件、人工原因、模型结果和操作审计|
|SQLite|接收异常时的本地待处理队列与旧包隔离|
|历史HTTP接口|查询超出短期缓存范围的历史趋势|
|本地模型文件与清单|加载经过筛选、验证的模型及关联信息|

Redis中收包状态使用Hash，最新值使用JSON字符串，趋势使用Stream。判定按小批次读取状态和需要的最新值，模型按需增量读取历史；采用有界超时，读取失败不作为点位离线证据。

当前生产部署仍可能依赖远程点位源数据库和历史接口，并非所有功能完全离线运行。本仓库不包含这些现场服务的生产参数。

## 7. 部署说明

本仓库为生产系统的脱敏源码副本，不是包含现场数据与模型的即装即用安装包。部署前需要准备兼容的Python环境、Redis、MySQL，以及合法可用的数据源、点位目录和模型产物。

1. 阅读[发布与部署说明](发布与部署说明.md)和各模块README，确认各进程依赖及Python版本要求。
2. 按模块安装requirements中的依赖；不同运行环境或模型依赖可能需要分开安装。
3. 将示例配置另存为本地实际配置，填写数据库、MQTT、接口和文件路径。
4. 部署实际点位目录；若启用模型，另行部署人工筛选范围、模型文件、验证状态和关联点清单。
5. 先确认Redis和数据库就绪，再启动接收、判定、模型与网页服务，并验证数据持续到达。
6. 按现场网络权限设置监听地址，其他电脑通过部署主机地址访问网页；上传GitHub不会自动部署生产网页。

实际凭据、现场导出、运行缓存、模型文件及生产配置不随源码上传。示例地址不能直接当作现场配置使用。早期训练命令和单目标配置见[历史试点参考](docs/早期轧钢试点与离线训练参考.md)，其中参数需要结合实际数据重新核对。

## 8. 验证与局限

仓库包含接收、缓存、规则、接口、模型相关逻辑和恢复策略的测试。测试通过只说明对应测试条件下的行为，不代表全厂所有故障模式均已覆盖。

接入全量传感器不等于全量模型诊断；通过验证不等于当前数据一定正常；健康度不应解释为未经校准的故障概率。模型可能受到历史异常、工况变化、关联信号共模错误和数据缺口影响。结论应结合现场工况、曲线与人工检查。

## 9. 发展方向

在现有全量数据接入与监测基础上，继续推进全链路可视化、模型辅助根因分析、统一采集与数据字典管理以及标准化部署。详见[未来规划](docs/未来规划.md)。规划不代表已经交付，也不改变当前各功能的实际实现边界。
